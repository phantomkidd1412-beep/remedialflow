# RCA — RemedialFlow "Crashed" on startup after re-publish (read-only)

**Deployment:** field-evidence-app-1 · **Re-publish run:** 93bfd382-df9f-4a0d-94e3-875376777877 (redeploy, succeeded 2026-11-13 00:59:09Z)
**Binary affected:** TestFlight/App Store Build 104, bundle com.emergent.fieldevidenceapp.pnhb44, Expo SDK 58

## Verdict
The re-publish DID deliver an OTA/EAS JS update to the existing Build 104 binary, and that update is **native-incompatible** with Build 104. This is the crash. The backend is healthy and is NOT the cause.

## (1) OTA delivery & runtimeVersion match — CONFIRMED MATCH (the policy did NOT prevent the update)
From the build's `eas-update` step (Cloud Build 9d337a33, step #7):
- `✔ Configured runtimeVersion for Android and iOS with "{"policy":"appVersion"}"` (line 269)
- `✔ Published!` → Branch **production**, **Runtime version 1.0.0**, Platform android+ios (lines 415–418)
- Update group ID `6ba737f7-40eb-4c08-8181-397e697da091`; iOS update ID `01a1d268-3d8d-7ad5-8e85-5ed31327b545`; Android update ID `01a1d268-3d8d-760e-98c0-126443d58b1c` (lines 419–421)
- Project `cf94c7db-5c8a-464e-bdb3-5961fdf21ccf`, EAS dashboard link at line 423

Why the policy did not protect Build 104: with `policy: appVersion`, the runtimeVersion equals the app's **version string** (`CFBundleShortVersionString`), NOT the build number. The published runtimeVersion is **1.0.0**. Build 104 is build *number* 104 of that same version 1.0.0, so its runtimeVersion is also 1.0.0. The build number is irrelevant to OTA eligibility under this policy. **Runtime versions match → Build 104 on branch `production` is eligible and will download/apply this JS.**

## Root cause
The new JS adds native modules — `expo-media-library (~58.0.14)`, `expo-background-task`, `expo-task-manager (~58.0.14)` — plus app.json `plugins`/`UIBackgroundModes` (fetch, processing) and `NSPhotoLibraryAddUsageDescription`. These are **native** code and are **not compiled into Build 104**. An OTA update ships only the JS bundle; it cannot add native modules to an already-installed binary. At startup the new JS resolves these native modules against a binary that lacks them → fatal native bridge/TurboModule resolution error → "RemedialFlow Crashed".

The `try/catch` guards (`src/backgroundUpload.ts` at module scope via `app/_layout.tsx`; `src/utils/galleryBackup.ts` lazy) do not save it: a missing native module fails at the native bridge/module-registration layer, which can throw before or outside the JS try boundary, and module-scope imports in `_layout.tsx` run during the earliest render path. Note: diagnosed from build evidence + Expo OTA semantics; NOT reproduced on-device (a native-module-missing crash requires the physical Build 104 binary and cannot be reproduced in the eph sandbox — no Xcode/native toolchain, no device).

## Suggested fix
**Immediate (stop the crashing for current Build 104 users):** roll back the `production` branch to the previous compatible update so Build 104 (runtime 1.0.0) gets JS that does NOT import the new native modules — either `eas update:rollback`/republish the prior known-good JS to branch `production` at runtimeVersion 1.0.0, or republish a 1.0.0 bundle with the native-module imports fully removed/guarded behind real runtime availability checks (not just try/catch of a module-scope import).

**Correct long-term:** adding native modules requires a NEW native binary AND a runtimeVersion change.
1. Bump the app `version` in app.json (e.g. 1.0.0 → 1.1.0) so future OTAs publish at runtimeVersion 1.1.0 and are no longer eligible for Build 104.
2. Generate and distribute a new native build (Build 105+) via Publish to App Store / Generate Build that actually includes expo-media-library, expo-background-task, expo-task-manager and the app.json plugin/permission changes.
3. Only then publish the feature JS — it will land on runtime 1.1.0 (the new binary) and Build 104 keeps its compatible 1.0.0 JS.

Do NOT just re-run the deploy on the same source: it will re-publish the same incompatible JS to runtime 1.0.0 and crash Build 104 again.
